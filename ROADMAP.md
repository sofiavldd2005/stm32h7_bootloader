## Phase 1 — Minimal Startup (The Embedonomicon, Ch. 1)
Goal: A binary that boots and spins in an infinite loop.
Tasks:
1. Write link.ld  
- MEMORY { FLASH (rx): ORIGIN = 0x08000000, LENGTH = 2M; RAM (rwx): ORIGIN = 0x20000000, LENGTH = 128K }  
- .vector_table at ORIGIN(FLASH): first entry = ORIGIN(RAM) + LENGTH(RAM) (initial SP), second entry = Reset vector  
- .text section after vector table  
- Discard .ARM.exidx (no unwinding)  
- ENTRY(Reset) + EXTERN(RESET_VECTOR)
2. Write Reset handler in Rust  
- #![no_std], #![no_main]  
- #[no_mangle] pub extern "C" fn Reset() -> ! { loop {} }  
- RESET_VECTOR static placed in .vector_table.reset_vector  
- #[panic_handler] → infinite loop
3. Build, flash, verify  
- cargo build --target thumbv7em-none-eabihf  
- cargo flash --chip STM32H755ZITx  
- Board should power up and sit quietly (no crash, no HardFault storm).
Why: This proves the vector table is at the right address, the CPU finds the reset vector, and the stack pointer is valid. Everything else builds on this.

## Phase 2 — Exception Handling (The Embedonomicon, Ch. 2)
Goal: All 14 core exceptions handled; user can override any handler.
Tasks:
1. In link.ld: after the reset vector, add .vector_table.exceptions section (space for 14 exception vectors).  
2. In Rust: EXCEPTIONS: [Vector; 14] external function array — NMI, HardFault, MemManage, BusFault, UsageFault, SVCall, PendSV, SysTick. Reserved entries = 0.  
3. DefaultExceptionHandler: loop {}  
4. In link.ld: PROVIDE(NMI = DefaultExceptionHandler), etc. This makes handlers weak — your #[no_mangle] pub extern "C" fn HardFault() overrides the default without needing linkage attributes.  
5. Test by triggering HardFault (e.g., read *VOID(0xFFFFFFFF) in Reset). Use cargo-flash + RTT or a breakpoint to confirm the handler fires.
Why: This mirrors the exact mechanism cortex-m-rt uses internally. After this phase, you understand how #[exception] works under the hood.

## Phase 3 — Clock & Power Configuration (STM32H7-specific)
Goal: Switch from HSI (default 64 MHz) to PLL1 @ 400 MHz, configure SMPS.
Tasks:
1. PWR configuration for SMPS  
- Nucleo-H755ZI-Q uses the internal SMPS regulator (boards with -Q suffix). Must configure PWR to enable SMPS before raising clock speed, otherwise the core will lock up.
2. Enable HSI64 oscillator.  
3. Configure PLL1:  
- PLLM = 4 (divide 64 MHz HSI → 16 MHz VCO input)  
- PLLN = 50 (16 MHz × 50 = 800 MHz VCO)  
- PLLP = 2 (800 / 2 = 400 MHz system clock)  
- PLLQ = 4 (200 MHz for kernel/peripheral clocks)  
- PLLR = 2 (reserved / trace)
4. Configure clock tree:  
- D1CPRE = /1 → CM7 core @ 400 MHz  
- HPRE = /2 → AHB @ 200 MHz  
- D2PPRE1, D2PPRE2, D1PPRE, D3PPRE = /2 → APB @ 100 MHz
5. Configure flash latency (2 wait states @ 200 MHz AHB).  
6. Switch system clock to PLL1.  
7. Verify: toggle an LED or probe SYSCLK via MCO pin.
Why: STM32H7 has the most complex clock tree of any Cortex-M STM32. Getting this wrong is the #1 cause of "board doesn't boot" in H7 projects. The power configuration (SMPS vs LDO) is subtle — wrong choice causes immediate lockup.

## Phase 4 — UART "Hello World"
Goal: Print "Hello World!\r\n" at 115200 8N1 on the ST-Link VCP.
Tasks:
1. Enable peripheral clocks: RCC → GPIO Port D, USART3.  
2. Configure GPIO PD8 (TX) and PD9 (RX) as alternate function AF7 (USART3_TX, USART3_RX), push-pull, pull-up.  
3. Initialize USART3:  
- Baud rate = 115200 (using UBRR = fCK / (8 × (2-OVER8) × BAUD))  
- 8 data bits, 1 stop bit, no parity, oversampling by 16  
- Enable TX, enable UART
4. Write blocking putc: poll TXE flag, write TDR.  
5. Write puts: send string bytes until \0, append \r\n.  
6. In Reset: call puts("Hello World!\r\n"), then loop {}.  
7. Open serial monitor (e.g., screen /dev/ttyACM0 115200) and verify output.
Why: USART3 is routed to the ST-Link VCP on PD8/PD9 on this board — no external USB-serial adapter needed. By writing the UART driver from scratch reading the RM0399 reference manual, you'll understand exactly how the peripheral works, which is --essential for the dual-core communication future phases.

## Phase 5 — Disable Cortex-M4
Goal: CM4 stays in reset so it doesn't execute garbage.
Tasks:
1. Use RCC to gate CM4: write RCC_MP_C1GR1 → set CM4RST bit to hold CM4 in reset.  
2. Verify: without this step, the CM4 boots from 0x08100000 (by default option bytes). If that flash region is unprogrammed, the CM4 will read all-ones (invalid opcode) and HardFault. Since the CM4's HardFault handler also points to unprogrammed memory, the core enters a lock-up state. While the CM7 won't crash from this, it wastes power and can cause peripheral arbitration issues.  
3. Alternative: For a cleaner separation, use STM32CubeProgrammer once to clear the BCM4 option byte (disabling CM4 boot at power-up). The pure-Rust approach via RCC is preferred for reproducibility.
Why: The H755 boots both cores by default. Leaving the CM4 running wild is undefined behavior — it might reconfigure shared peripherals your CM7 is using.
